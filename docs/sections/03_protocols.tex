\section{Protocolos de Comunicación: Gateway A2A y JSON-RPC 2.0}
\label{sec:protocols}

\subsection{Especificación del Estándar A2A (Agent-to-Agent)}
El estándar A2A establece un marco formal e interoperable para la comunicación entre sistemas multiagente autónomos. Sobre la capa de transporte seguro (HTTPS / mTLS con soporte HTTP/1.1 y HTTP/2), el intercambio de mensajes se articula mediante el protocolo de invocación remota JSON-RPC 2.0. Esta decisión arquitectónica desacopla el transporte de la semántica transaccional, asegurando que cada orden emitida contenga identificadores deterministas (\texttt{id}) y un cuerpo fuertemente tipado.

\subsection{Publicación de Metadatos: Endpoint /.well-known/agent.json}
El anclaje semántico y punto de entrada para el descubrimiento dinámico por parte de agentes externos es el endpoint estandarizado:
\begin{center}
    \texttt{GET /.well-known/agent.json}
\end{center}

Este endpoint expone públicamente la \textbf{Agent Card} del sistema. Para maximizar el rendimiento perimetral y alcanzar un patrón de cero asignaciones de memoria (\textit{zero-allocation}), el Gateway procesa y serializa la Agent Card durante la fase de inicialización (\textit{bootstrap}) del host Kestrel, almacenando el payload resultante en un búfer inmutable UTF-8 (\texttt{ReadOnlyMemory<byte>}). Cada petición entrante a esta ruta es despachada directamente desde memoria con encabezados de control de caché (\texttt{Cache-Control: public, max-age=300}) y tipo de contenido \texttt{application/json; charset=utf-8}, eliminando cualquier latencia de serialización en tiempo de ejecución.

La Agent Card comprende las siguientes secciones normativas:
\begin{itemize}
    \item \textbf{Identidad y Metadatos:} Identificador URI único (\texttt{id}), nombre descriptivo, versión semántica y versión de especificación del protocolo A2A.
    \item \textbf{Capacidades Declaradas (\textit{Capabilities}):} Listado de extensiones funcionales, tales como orquestación stateless, soporte estricto de JSON-RPC 2.0 y control de cuotas mediante ventanas deslizantes.
    \item \textbf{Catálogo de Habilidades (\textit{Skills}):} Definición formal de cada método habilitado (\texttt{create\_task}, \texttt{send\_message}, \texttt{get\_task}, \texttt{cancel\_task}) acompañado de su esquema JSON (\textit{JSON Schema}) de parámetros de entrada (\texttt{inputSchema}) y salida (\texttt{outputSchema}).
    \item \textbf{Seguridad Perimetral:} Esquemas de autenticación reconocidos (\texttt{X-Agent-ID}, certificados mTLS X.509) y límites de tasa nominales.
\end{itemize}

\subsection{Protocolo de Handshake y Negociación de Agent Cards}
Antes de dar inicio formal a una negociación comercial, los agentes y sus respectivas entidades (\textit{tenants}) deben establecer un canal seguro de confianza mutua mediante el protocolo de \textit{handshake} (apretón de manos). Este procedimiento garantiza que únicamente contrapartes autorizadas y verificadas puedan acceder al catálogo de servicios y comenzar el intercambio de propuestas.

Tal como se detalla en la Figura~\ref{fig:handshake_flow}, el flujo opera a través de las siguientes fases secuenciales:
\begin{enumerate}
    \item \textbf{Solicitud de Conexión y Validación de Identidad:} El \textit{Tenant A} manifiesta su intención de negociar con el \textit{Tenant B} a través del software orquestador. El sistema procede inmediatamente a validar las credenciales de identidad del \textit{Agente A}. En caso de discrepancia criptográfica o firma inválida, la sesión se aborta con error terminal.
    \item \textbf{Verificación en Lista Blanca (\textit{Whitelist}):} El orquestador consulta al \textit{Tenant B} para verificar si el \textit{Tenant A} figura en su lista de confianza permitida. Si la verificación resulta desfavorable, la comunicación se clausura impidiendo accesos no autorizados.
    \item \textbf{Entrega del Catálogo de Agent Cards:} Una vez aprobada la conexión, el \textit{Tenant B} suministra su catálogo de tarjetas de agente (\textit{Agent Cards}) disponibles. El orquestador transmite dicho catálogo al \textit{Agente A}.
    \item \textbf{Selección de Habilidad y Validación Cruzada:} El \textit{Agente A} inspecciona el catálogo y selecciona la tarjeta de agente idónea para la transacción. Si el agente requerido no está disponible, el flujo finaliza con estado \texttt{DECLINE}. Si existe, se emite una orden de selección (\texttt{SELECT}), tras la cual ambas partes ejecutan una verificación mutua de credenciales con el \textit{Agente B} antes de dar por completado el apretón de manos y transicionar al estado operativo inicial \texttt{on\_board}.
\end{enumerate}

\subsection{Pipeline de Validación en Cascada en 4 Fases}
Para garantizar la integridad del sistema frente a cargas malformadas, intentos de inyección o inconsistencias de secuencia, el Gateway A2A canaliza cada petición recibida en los endpoints \texttt{POST /rpc} o \texttt{POST /a2a} a través de un pipeline modular en cascada organizado en cuatro fases secuenciales bajo el principio de fallo rápido (\textit{fail-fast}):

\begin{enumerate}
    \item \textbf{Fase 1: Validación de Transporte y Formato JSON-RPC 2.0:}
    Examina que el cuerpo HTTP contenga un documento JSON sintácticamente correcto. Si el analizador léxico falla, se genera de inmediato una respuesta con código de error \texttt{-32700} (\textit{Parse error}). A continuación, verifica que el elemento raíz sea un objeto JSON y contenga los campos obligatorios: \texttt{"jsonrpc": "2.0"}, \texttt{"method"} (cadena de caracteres no vacía) y \texttt{"id"} (identificador numérico o alfanumérico). Si alguno de estos campos falta o es inválido, se emite el error \texttt{-32600} (\textit{Invalid Request}).

    \item \textbf{Fase 2: Validación de Conformidad de Esquema de Parámetros:}
    Evalúa que la propiedad \texttt{"params"} exista y corresponda a un objeto estructurado. Si el método solicitado coincide con una habilidad registrada en la Agent Card, se valida la presencia y tipado de sus argumentos mandatorios (por ejemplo, \texttt{tenant\_id} y \texttt{skill} en \texttt{create\_task}, o \texttt{negotiation\_id}, \texttt{turn\_index} y \texttt{sender\_id} en \texttt{send\_message}). Si los parámetros no son conformes, se interrumpe la ejecución con el error \texttt{-32602} (\textit{Invalid params}). Si el método no es reconocido en esta fase, la petición avanza hacia la Fase 3 sin rechazarla prematuramente por parámetros.

    \item \textbf{Fase 3: Validación Semántica contra la Agent Card:}
    Verifica mediante búsqueda de complejidad $O(1)$ en el catálogo inmutable (\texttt{FrozenDictionary}) que el método solicitado figure entre las habilidades (\textit{Skills}) habilitadas en la Agent Card activa. En caso de invocar una habilidad inexistente o no autorizada, se rechaza la llamada emitiendo el código formal \texttt{-32601} (\textit{Method not found}).

    \item \textbf{Fase 4: Coherencia Estructural de Turno y Correlación (Gateway Passthrough):}
    Bajo el patrón arquitectónico \textit{Gateway Passthrough}, el Gateway no consulta el almacén de estado en Redis ni computa las transiciones de la Máquina de Estados Finitos (FSM), dado que dicha lógica de negocio corresponde exclusivamente al núcleo del Orquestador. En esta fase, el componente \texttt{ITurnGuardService} se limita a verificar la presencia y validez estructural de \texttt{negotiation\_id}, comprobar que \texttt{turn\_index} sea un entero no negativo ($\ge 0$) y asegurar la correlación de identidad perimetral verificando que el \texttt{sender\_id} declarado coincida estrictamente con la entidad autenticada en \texttt{AgentIdentityContext}.
\end{enumerate}

\subsection{Despacho Desacoplado y Mapeo de Excepciones de Dominio}
Superadas las cuatro fases del pipeline, el Gateway empaqueta la carga útil en un sobre de transporte desacoplado:
\begin{center}
    \texttt{A2ACommandEnvelope(NegotiationId, Method, Payload, Emisor, TurnIndex)}
\end{center}
Este sobre se transfiere mediante inyección de dependencias a la interfaz \texttt{INegotiationDispatcher}. Si durante el procesamiento en el dominio de orquestación la FSM detecta que el turno no corresponde al emisor, que el índice de turno es extemporáneo o duplicado, o que existe una colisión de concurrencia, el orquestador propaga una excepción de dominio \texttt{TurnConflictException} (o \texttt{TurnOutOfOrderException}).

El Gateway intercepta dicha excepción en el perímetro perimetral y la transforma de forma canónica en una respuesta formal JSON-RPC 2.0 con el código de servidor reservado \texttt{-32001} (\textit{Turn Conflict / Out of Order}), retornando los metadatos de diagnóstico correspondientes.

\subsection{Seguridad Perimetral y Control de Acceso}
El Gateway aplica directivas perimetrales antes de procesar el payload:
\begin{itemize}
    \item \textbf{Extracción de Identidad (\texttt{AgentIdentityContext}):} Inspecciona la cabecera estándar \texttt{X-Agent-ID} y el atributo Common Name (CN) del certificado de cliente en enlaces mTLS X.509, estableciendo un contexto de identidad inyectable por petición (\textit{scoped}).
    \item \textbf{Rate Limiting Particionado:} Utiliza el middleware nativo \texttt{Microsoft.AspNetCore.RateLimiting} configurado bajo un algoritmo de ventana deslizante (\textit{Sliding Window}). Las particiones se aíslan de manera estricta por el identificador de cliente (\texttt{AgentId}), garantizando que ráfagas excesivas de peticiones de un agente deriven en respuestas inmediatas \texttt{429 Too Many Requests} sin afectar la cuota de agentes competidores.
\end{itemize}

\subsection{Arnés de Pruebas de Integración E2E y Verificación Continua (CI)}
\label{sec:e2e_testing_ci}
Para garantizar la estabilidad operativa del Gateway A2A y validar empíricamente el cumplimiento del estándar JSON-RPC 2.0 frente a cargas de trabajo realistas, se ha diseñado un arnés de pruebas de integración \textit{End-to-End} (E2E) basado en agentes simulados deterministas y un flujo automatizado de Integración Continua en GitHub Actions.

\subsubsection{Arquitectura de Agentes Simulados Deterministas}
A diferencia de los enfoques basados en modelos de lenguaje extensos (LLM), cuyos tiempos de respuesta no deterministas y costes de inferencia introducen variabilidad y fragilidad en los entornos de prueba, el arnés implementa dos agentes sintéticos gobernados por máquinas de estados finitos y reglas deterministas de fijación de precios en el espacio de parámetros comerciales:
\begin{itemize}
    \item \textbf{Agente Comprador (\texttt{BuyerAgent}):} Identificado como \texttt{urn:agent:buyer}. Inicia la interacción con una oferta inicial reducida ($p_0 = 75{,}00$\,EUR), un techo de reserva infranqueable ($p_{\text{max}} = 95{,}00$\,EUR) y un incremento incremental fijo por turno ($\Delta p = +5{,}00$\,EUR). Emite la cabecera perimetral obligatoria \texttt{X-Agent-ID: urn:agent:buyer}. Acepta la propuesta (\texttt{action: ACCEPT}) si el precio ofertado por la contraparte satisface $p_{\text{recibido}} \le p_{\text{max}}$.
    \item \textbf{Agente Vendedor (\texttt{SellerAgent}):} Identificado como \texttt{urn:agent:seller}. Parte de una postura inicial elevada ($p_0 = 105{,}00$\,EUR), un suelo de reserva mínimo admisible ($p_{\text{min}} = 85{,}00$\,EUR) y un decremento fijo por turno ($\Delta p = -5{,}00$\,EUR). Emite la cabecera perimetral \texttt{X-Agent-ID: urn:agent:seller}. Acepta la propuesta si $p_{\text{recibido}} \ge p_{\text{min}}$.
\end{itemize}

Dado el solapamiento en el intervalo de reserva $[85{,}00,\, 95{,}00]$\,EUR, el sistema garantiza matemáticamente una convergencia finita en $N \le 5$ turnos, produciendo un acuerdo vinculante con precio final de $95{,}00$\,EUR sin derivar en bucles infinitos.

\subsubsection{Casos de Prueba Automatizados}
El ejecutor de pruebas (\texttt{run\_simulation.py} y suite \texttt{test\_simulation.py} en \texttt{pytest}) evalúa dos suites principales contra el Gateway:
\begin{enumerate}
    \item \textbf{Caso de Prueba 1: Negociación Determinista Concurrente (\textit{Happy Path}):}
    Simula el intercambio alternado de turnos monótonos crecientes (\texttt{turn\_index}: $0, 1, 2, 3, 4$). Cada mensaje es validado por las cuatro fases del pipeline y despachado hacia el orquestador desacoplado, asegurando que cada respuesta HTTP 200 contenga la estructura canónica JSON-RPC con \texttt{"status": "acknowledged"}, preservación estricta del \texttt{negotiation\_id} y concordancia de \texttt{turn\_index}.
    \item \textbf{Caso de Prueba 2: Detección y Confinamiento de Anomalías Perimetrales (Código \texttt{-32602}):}
    Inyecta intencionadamente anomalías estructurales para verificar que el Gateway aplique el principio de fallo rápido (\textit{fail-fast}) sin provocar excepciones no controladas ni respuestas de error interno del servidor (HTTP 500):
    \begin{itemize}
        \item \textit{Índice de turno negativo:} Se remite un payload con \texttt{turn\_index: -1}, provocando el rechazo inmediato en Fase 2/4 con código JSON-RPC \texttt{-32602} (\textit{Invalid params}).
        \item \textit{Omisión de propiedades mandatorias:} Se transmite una solicitud donde se suprime la clave requerida \texttt{message}, interceptada en Fase 2 con código \texttt{-32602}.
        \item \textit{Discrepancia de identidad perimetral:} Se configura la cabecera HTTP \texttt{X-Agent-ID: urn:agent:buyer} mientras que el cuerpo declara \texttt{sender\_id: urn:agent:seller}. El componente \texttt{TurnGuardFilter} (Fase 4) detecta la suplantación y rechaza la orden con código \texttt{-32602} y mensaje explicativo (\textit{Identity mismatch}).
    \end{itemize}
\end{enumerate}

\subsubsection{Pipeline de Integración Continua en GitHub Actions}
La automatización del ciclo de vida se formaliza en el workflow \texttt{.github/workflows/a2a-gateway-ci.yml}, activado en cada \textit{push} y \textit{pull request} sobre las ramas \texttt{main} y \texttt{develop}. El flujo ejecuta la siguiente secuencia determinista:
\begin{enumerate}
    \item \textbf{Compilación y Pruebas Unitarias .NET:} Restaura dependencias y compila la solución en configuración \texttt{Release} sobre el SDK de .NET 9.0, ejecutando las pruebas de integración en C\#.
    \item \textbf{Preparación del Entorno Python:} Configura Python 3.11 e instala las librerías de prueba (\texttt{httpx}, \texttt{pydantic}, \texttt{pytest}) con caché de dependencias.
    \item \textbf{Arranque Asíncrono del Gateway Kestrel:} Lanza el host de ASP.NET Core en segundo plano en \texttt{http://127.0.0.1:5000} registrando su identificador de proceso (PID) y redirigiendo la salida a \texttt{gateway.log}.
    \item \textbf{Sondeo de Disponibilidad (\textit{Healthcheck Polling}):} Realiza un bucle de espera activa (hasta 30 segundos) consultando el endpoint de la Agent Card (\texttt{GET /.well-known/agent.json}) para asegurar que el servidor esté plenamente inicializado antes de emitir tráfico.
    \item \textbf{Ejecución de Suites E2E:} Dispara tanto el ejecutor nativo \texttt{run\_simulation.py} como la suite \texttt{pytest}, validando la convergencia bilateral y el confinamiento de errores perimetrales.
    \item \textbf{Diagnóstico y Apagado Limpio:} Si ocurre un fallo en cualquier paso previo (\texttt{if: failure()}), vuelca el contenido completo de \texttt{gateway.log} para facilitar el triaje. Finalmente, mediante \texttt{if: always()}, envía la señal de terminación al PID del Gateway asegurando la liberación limpia de puertos y recursos del sistema operativo.
\end{enumerate}
